# feat: npx skills install commands

## Overview

Add copyable `npx skills` (skills.sh) install commands across Systematic's docs surfaces as a prominent secondary install path. The npm plugin stays the primary/recommended path (full OpenCode runtime); `npx skills add marcusrbrown/systematic` is the portable, multi-harness alternative installing the bundled SKILL.md content. The whole-collection command lands on the homepage, README, and installation page; a per-skill command is auto-injected into each generated skill reference page. Each surface presents both paths with a chooser cue, the plugin visually primary (not a 50/50 choice).

## Problem Frame

Systematic's only documented install is the npm plugin (OpenCode-specific). The bundled skills are harness-agnostic SKILL.md content with no one-command install for other harnesses or for users who just want the skill content. `npx skills` (vercel-labs/skills) is the idiomatic agent-skills installer — it pulls directly from any GitHub repo with SKILL.md files (no registry), is harness-aware, and matches how comparable collections present install. See origin: `docs/brainstorms/2026-06-06-npx-skills-install-commands-requirements.md`.

## Requirements Trace

- R1. Whole-collection command `npx skills add marcusrbrown/systematic` is a copyable code block on homepage, README, and installation page.
- R2. npm plugin is the primary/recommended path; `npx skills` is the prominent secondary/alternative path (not co-equal in hierarchy). Each surface states what each path delivers AND what `npx skills` does NOT give (it installs skill content only — no slash-command registration, no bootstrap injection, no `systematic_skill` tool; those come from the plugin).
- R3. Each generated NON-DEPRECATED skill reference page carries `npx skills add marcusrbrown/systematic --skill <name>` (where `<name>` is the frontmatter `name`, e.g. `ce:plan`), injected by `docs/scripts/transform-content.ts`. Deprecated skills (those with a `deprecated:` frontmatter block — e.g. `orchestrating-swarms`, `claude-permissions-optimizer`) do NOT get a per-skill install command (we don't advertise installing skills slated for removal).
- R4. Agent reference pages unchanged.
- R5. Installation page documents `npx skills` usage: `-a <agent>`, `-g`, `--list`, `--skill`.
- R6. Homepage dual-path block and per-skill page command-slot visual treatment are owned by @designer; orchestrator/implementer owns README, installation page, and the generator wiring (emitting @designer's markup).
- R7. Per-skill commands use the frontmatter `name` (canonical, matches `--list`); colon-form names like `ce:plan` are valid CLI args.
- R8. Each surface presents a chooser cue (one-line selector beside each path) and keeps the plugin visually primary, not a 50/50 choice. The chooser cue reinforces plugin-primary, not parity.
- R9. Installation page presents the two paths first, then a scannable (table or compact list, not prose) treatment of the `npx skills` flag variants.
- R10. Per-skill command sits in a fixed slot near the top of each skill page, adjacent to the existing "View source" header.
- R11. Every install command is a single-line fenced code block (Starlight's built-in copy button; no custom component).

## Scope Boundaries

- Not changing the npm-plugin flow or making it secondary.
- Not adding install commands to agent reference pages.
- Not building a custom copy-button component.
- Not publishing to or depending on a skills.sh registry.
- Not restructuring the OCX guide.

### Deferred to Separate Tasks

- Harness-specific plugin-marketplace install paths (Claude Code `/plugin install`, etc.): future, only if a marketplace presence is established.

## Context & Research

### Relevant Code and Patterns

- `docs/scripts/transform-content.ts` — generates per-skill pages. The `definition-header` block (the "View source" div, ~line 125-127) is assembled by `generateHeader`/`generatePage(frontmatter, body, header)` (~line 309); the skill's `name` is already resolved (`deriveName`, ~line 132; passed as `name` into `transformFrontmatter`). The per-skill command slot is this header block (R10).
- `docs/src/content/docs/getting-started/installation.mdx` — current install is a `<Steps>` block with the plugin JSON (~line 17-44). The `npx skills` secondary section + flag variants slot in after it.
- `docs/src/content/docs/index.mdx` — homepage; `npx skills` whole-collection command + chooser-cue dual-path block (@designer).
- `README.md` — Quick Install section (~line 34-42); add the whole-collection command + chooser cue.
- `docs/src/content/docs/reference/skills/*` — generated skill pages (regenerated by the generator; not hand-edited).

### Institutional Learnings

- Generated reference pages must not be hand-edited; changes go in the generator (`transform-content.ts`) and regenerate. Memory: `bun run docs:build` is the real gate (not `docs:generate` alone).
- `npx skills --skill` matches the frontmatter `name` (and directory) case-insensitively, no normalization; colon-form valid (verified against vercel-labs/skills source).

## Key Technical Decisions

- **Per-skill command via the generator** (R3): inject into the existing `definition-header` block using the already-resolved `name`. One generator change covers all ~46 skills; regenerating reproduces it. No per-page hand-maintenance.
- **Chooser cue makes the dual path coherent** (R8): a one-line selector beside each path + plugin visual primacy resolves the "which do I run?" risk reviewers raised. Both paths are available and documented; the plugin is primary in hierarchy.
- **Ownership boundary** (R6): Unit 4 (@designer) owns the homepage dual-path block and the *visual/spec contract* for the per-skill slot (wrapper presentation). Unit 1 (implementer) owns the generator implementation that emits the slot — it ships against a fixed default and absorbs @designer's non-breaking refinement. Orchestrator owns README + installation page (structural/content).
- **Single-line fenced blocks** (R11): rely on Starlight's auto copy buttons; no custom component.

**Approach:**
- **Prerequisite refactor:** `transform-content.ts` currently exports nothing and runs generation side effects at module load. - **Thread name + type:** `generateDefinitionHeader` does not currently receive `name` — it's only in scope in `processDirectory`. Add `name` and a skill/agent discriminator to the header generator's params and pass them from `processDirectory`'s `generatePage(...)` call.
- **Inject command (skills only):** in the header block (the `definition-header` div), add a single-line fenced `npx skills add marcusrbrown/systematic --skill <name>` using the resolved skill `name`. Only for `definitionType === 'skill'`; agent pages get nothing (R4).
- **Skip deprecated:** if the skill's frontmatter has a `deprecated:` block, do NOT emit the command (R3). The frontmatter is already parsed in scope.
- Use a fixed default slot; @designer (Unit 4) refines presentation later without breaking the generator contract.

**Patterns to follow:**
- The existing `definition-header` / "View source" assembly in `transform-content.ts`.

**Test scenarios:**

- Edge case: a skill whose `name` falls back to the directory basename still emits a valid command.
- Error path: a DEPRECATED skill (frontmatter has `deprecated:`) emits NO per-skill command.

**Verification:**

## System-Wide Impact

- **API surface parity:** the per-skill command is generated, so all skills get it consistently; adding/removing a skill auto-includes/excludes the command.
- **Unchanged invariants:** npm-plugin flow unchanged; agent pages unchanged; OCX guide unchanged; no new runtime/plugin code.
- **Generated-artifact rule:** skill pages are regenerated — never hand-edit; the command lives in the generator.

## Risks & Dependencies

| Risk | Mitigation |
|------|------------|
| Per-skill `--skill` arg wrong for colon-form names | Verified `npx skills --skill` matches frontmatter `name` incl. colons; Unit 1 tests a colon-form name explicitly. Generator does not add quoting; the colon-form is shell-safe as a bare arg. |
| Deprecated skills get advertised install commands | Unit 1 skips per-skill commands for skills with a `deprecated:` frontmatter block; tested explicitly. The whole-collection command still installs everything `npx skills` resolves — acceptable, as the plugin/catalog filtering is a separate concern and `npx skills` is a content installer. |
| Dual path causes "which do I run?" confusion | Chooser cue (R8) + plugin visual primacy on every surface; R2 states what `npx skills` does NOT give. |
| Generator refactor (export + `import.meta.main` guard) changes run behavior | The guard preserves the existing top-level run; only adds importability. Verified by `bun run docs:build` producing identical output. |
| @designer presentation and generator slot drift | Unit 1 ships a fixed default slot; Unit 4 refines non-breaking presentation only — no hard sequencing gate. |
| Generated pages hand-edited by mistake | Change lives only in the generator; `docs:build` regenerates. |

## Documentation / Operational Notes

- Run `bun run docs:generate` then `bun run docs:build` to regenerate skill pages and verify MDX parses.
- Registry drift unaffected (skill page content isn't registry input), but run `bun run registry:drift` in the gate to confirm.
