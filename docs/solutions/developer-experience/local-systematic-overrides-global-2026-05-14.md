# Project-local Systematic output overrides global Systematic output

## Context

Systematic contributor sessions can intentionally load two Systematic plugin
sources: a user/global npm package and the project-local `./src/index.ts` from
the repo checkout. OpenCode runs each plugin source's config hook, so the local
hook can see agents, commands, and skill paths that were emitted by the earlier
global hook.

The broken behavior looked like a native OpenCode conflict:

```text
agents.systematic-implementer conflicts with native OpenCode agent.systematic-implementer
```

That framing was wrong. In this repo, the project-local plugin is the source
under development and must supersede earlier Systematic-emitted output. Earlier
global Systematic output is not user-owned native config; treating it that way
breaks the standard local-development setup.

## Guidance

When merging Systematic-emitted config into OpenCode config, split existing
entries into two groups:

1. **Prior Systematic output** — generated by an earlier Systematic plugin hook
   in the same startup. This can be replaced by the later project-local hook.
2. **True native/user config** — entries owned by OpenCode or the user's config.
   These keep existing-config-wins semantics.

The merge order should be:

```text
const merged = preserveNativeAndUserEntries(existing)
addCurrentSystematicEntriesUnlessNativeConfigExists(merged, emitted)
```

The shipped fix applies that shape in `src/lib/config-handler.ts` for emitted
agents and commands, and refreshes `skills.paths` so the local checkout's
bundled skills directory wins over stale prior Systematic paths.

Tests should prove both sides of the boundary:

```ts
expect(config.agent?.['systematic-implementer']?.prompt).toContain(
  'Agent prompt for systematic-implementer.',
)
expect(config.agent?.['systematic-implementer']?.temperature).toBe(0.25)
expect(config.agent?.['native-agent']).toEqual({
  description: 'Native agent',
  prompt: 'native prompt',
})
```

This verifies that project-local Systematic output replaces stale global
Systematic output while native/user config and user overlays still survive.

## Why This Matters

- **Contributor DX depends on deterministic local precedence.** A checkout that
  loads `./src/index.ts` must exercise the code under development, not stale
  globally installed package output.
- **The bug is not an end-user config error.** Asking contributors to remove
  their global Systematic install or user overlays hides the source of the
  problem and makes local development brittle.
- **OpenCode multi-source plugin registration is expected behavior.** Systematic
  has to be idempotent across its own emitted output instead of assuming every
  earlier config entry is native/user-owned.

## When to Apply

- When adding or changing Systematic-generated OpenCode config for emitted
  agents, skills-as-commands, commands, or `skills.paths`.
- When a local `./src/index.ts` development session behaves differently from an
  isolated test fixture.
- When an OpenCode startup conflict involves a `systematic-*` key or a bundled
  Systematic asset name.

## Examples

Wrong mental model:

```text
same key already exists -> native/user conflict -> fail or skip local output
```

Correct contributor-development model:

```text
same key already exists
  -> if prior Systematic output: replace with local emitted output
  -> if true native/user config: preserve existing config
```

Verification for this class of bug should include unit-level merge tests. For
host-order regressions, use an isolated mixed-version OpenCode probe that loads
the published package first and the local checkout second, then inspects the
agent-observable config surface.

## Follow-up Caveats

- Systematic-origin detection is currently heuristic. Tighten it when changing
  these predicates so user-authored entries that merely look Systematic-branded
  are not discarded by accident.
- Skill path cleanup should stay narrow enough to remove prior Systematic paths
  without removing unrelated user paths that happen to contain a
  `systematic/skills` segment.
