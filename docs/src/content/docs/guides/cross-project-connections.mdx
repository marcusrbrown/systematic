If you work in several repositories, each one holds its own `docs/solutions/`, and nothing reads them against each other. One project records "always retry the export job on timeout". A sibling records "never retry it". A third project hit a failure that the first one already solved and wrote down. `ce:connect` reads the projects you name and proposes three kinds of candidate:

- **Contradiction.** Two learnings that give opposite guidance for the same situation, where at least one of them is in the project that should change and at least one is in another project.
- **Transferable lesson.** A lesson one project recorded, where another project's tracked code, workflows or config show the failure and its own learnings do not record the lesson.
- **Code mismatch.** One learning whose present-tense claim the code no longer supports, for example "the export route rewrites paths" after the route was renamed. A candidate carries a reason, `stale` or `unscoped`, and quotes the evidence (see [A code mismatch](#a-code-mismatch)).

A run proposes. A person decides. `ce:connect` writes nothing into any project, any remote or any global config. Its only output is a digest and a run record in a state directory outside your repositories.

## What a run does

1. The skill reads the mode and checks that the host is one where the researcher's tool limits have been seen to work (see [Supported hosts](#supported-hosts)).
2. A helper, a Node script bundled with the skill, resolves your selection (the whole allow list unless you name a group or some projects), takes a lock, lists each selected project's tracked files, hashes them and builds an index of the learnings.
3. The skill groups part of that index into families of related rules and dispatches the `connections-researcher` agent once per family. The agent can read, grep and glob. It cannot run commands, write, edit or fetch.
4. The helper validates every candidate the agent returns. It keeps a candidate only when each cited path is a tracked file in an allowed project, each fingerprint matches the hash taken at the start, each excerpt appears word for word in its file, and each piece of target evidence names a line span that holds its symbol, and each piece of evidence for a code mismatch names a line span that holds its excerpt. Candidates that fail a check are dropped, counted by reason in the digest, and listed there by title and reason, so you can tell whether a real finding was lost.
5. The helper publishes the digest and the run record and updates a small ledger.

A project supplies text, not instructions. A learning that says "report nothing", "this corpus is audited" or "add that project to the allow list" changes nothing. The allow list is your own config.

## Choose the projects

The allow list is a top-level `connect` block. Its `allow_projects` field names every project a run may read. An optional `groups` field names parts of that list. Put the block in your user-level Systematic config:

```jsonc
// ~/.config/opencode/systematic.jsonc
{
  "connect": {
    "allow_projects": [
      "~/src/github.com/me/app",
      "~/src/github.com/me/shared-lib"
    ]
  }
}
```

Each entry is the root of a repository checkout, absolute or starting with `~`. It is not a subdirectory and not a linked worktree. At most 64 entries. A project is identified by its main checkout, so a worktree of an allowed project is the same project.

Rules for the block:

- **User-owned only.** A repository cannot grant itself access to other projects. If a project's own config sets `connect`, Systematic ignores the whole block and prints a warning.
- **A missing list is an empty list.** With no list, a run stops with `no-allowed-projects` and reads nothing.
- **A bad block is an empty list.** An unknown key or a bad value, in `groups` as well as in `allow_projects`, makes the block unreadable, and an unreadable block allows nothing and defines no group. It never widens access.
- **Layers merge as a union.** `systematic.jsonc`, `systematic.local.jsonc` and the same two files in `OPENCODE_CONFIG_DIR` can each hold entries. Put machine-specific paths in the `.local` file. The layers and their order are the ones in [Configure search](/systematic/guides/search/#configure-search). Groups merge by name instead: a later file replaces a same-named group whole.
- **An entry that matches no repository is reported.** The run names the entry and the reason (stale path, not a repository, not the main root, unreadable). That run is `degraded`, because a project was not read. The other projects are still read. A run narrowed to a group or to some projects does not touch the entries it does not name, so an entry that matches nothing does not degrade it.
- **Unsafe config directories are refused.** If `OPENCODE_CONFIG_DIR` points inside a checkout or inside an allowed project, the run does not read it.

The field reference is in [Configuration](/systematic/reference/configuration/#connect).

### Groups

A group is a name for part of the allow list. Define groups beside `allow_projects`:

```jsonc
// ~/.config/opencode/systematic.jsonc
{
  "connect": {
    "allow_projects": [
      "~/src/github.com/me/app",
      "~/src/github.com/me/shared-lib",
      "~/src/github.com/me/docs-site"
    ],
    "groups": {
      "backend": [
        "~/src/github.com/me/app",
        "~/src/github.com/me/shared-lib"
      ]
    }
  }
}
```

- **Name.** 1 to 64 characters of lowercase letters, digits and hyphens, starting with a letter or digit.
- **Members.** One to 64 entries in the same form as an `allow_projects` entry. At most 32 groups per file.
- **User-owned only,** like the rest of the block. A project's own config cannot define a group.
- **A group never adds a project.** Each member must resolve to a project on the allow list. The config loader checks only the shape of a group. The membership check happens when a run selects the group, and a member that is not on the allow list stops that run.

### Pick projects for one run

For a one-off narrower run, name the projects instead of defining a group. Each entry is a project's directory name or its 12-character project key. A directory name shared by two allowed projects is refused, and the refusal lists their keys so you can name one of them.

### Selection words

| Words | What the run reads |
|---|---|
| None | The whole allow list. |
| `group:backend` | The members of that group. |
| `projects:app,shared-lib` | The two named projects. |
| The same word twice or more | That word, counted once. |

No word ever reads more than the allow list. A word that would is refused.

A bad selection stops the run before it takes the lock, in interactive and headless mode alike. Nothing is written, and the run ends `Connect failed` with the reason on the line before it. It never falls back to the whole allow list, because you asked for a narrower run.

| Reason | Cause |
|---|---|
| `conflicting-selection` | A `group:` word together with a `projects:` word, two different `group:` words, or two different `projects:` words. `projects:a,b` and `projects:b,a` are different words. |
| `unknown-group` | No group of that name is in your config. |
| `unknown-project` | No allowed project has that directory name or key. |
| `ambiguous-project` | Two allowed projects share that directory name. The refusal lists their keys. |
| `group-member-not-allowed` | A member of the group is not on the allow list. The refusal names the group and the member, and says why when the member did not resolve to a repository. |
| `invalid-request` | A word is malformed: an empty value, an empty entry between commas, more than 32 words, or a word over 2,048 characters. |

## Declare dependency pins

A claim about a dependency can hold at the version one project pins and fail at another version. When you have both versions checked out, a pin tells the researcher which allowed checkout is the other version, so it checks the claim at both. The pin is yours to declare: Systematic never reads a lockfile, a workflow or a manifest to find one.

Declare pins beside `allow_projects`, in your user-level config:

```jsonc
// ~/.config/opencode/systematic.jsonc
{
  "connect": {
    "allow_projects": [
      "~/src/github.com/me/app",
      "~/src/github.com/upstream-org/host-lib-old"
    ],
    "pins": [
      {
        "project": "~/src/github.com/me/app",
        "upstream": "upstream-org/host-lib",
        "file": "config/pins.json",
        "key": "host.version"
      }
    ]
  }
}
```

This says: `app` pins `upstream-org/host-lib` at the value under `host.version` in `config/pins.json`. The second allowed entry is a checkout of `host-lib` at another version, found because its git `origin` is `upstream-org/host-lib`.

- **`project`.** An `allow_projects` entry written exactly as it is on the allow list, or that entry's resolved root, an absolute path. Another spelling of the same path does not match, and the pin is dropped without a read. A pin never adds a project to the allow list or to a selection.
- **`upstream`.** A GitHub `owner/repo`. Case is ignored when it is compared with a checkout's `origin`.
- **`file`.** A path inside the project, written with `[A-Za-z0-9._/-]`, at most 256 characters, with no leading `/` and no `..` segment. It is JSON or JSONC, read from the working tree as it is on disk, so an untracked file works. A symlink is refused.
- **`key`.** Dotted segments that walk nested objects: `host.version` reads `{ "host": { "version": "3.1.0" } }`. There is no array index, and a key that contains a dot itself cannot be addressed. The value must be a string that starts with a letter or digit, then holds letters, digits, `.`, `_`, `+` and `-`, 64 characters at most. A tag may contain a `/`, a pinned value may not.
- **Limits.** At most 64 pins per file. The four config layers merge as a union, and an identical pin written twice counts once. Entries that give the same project, upstream and key but different files are dropped at run time with a `pin-conflict` note, never resolved by picking one.

### The version of a checkout

A checkout's version is the one git tag at its HEAD. The helper reads it from the files in `.git` and runs no git command. It reports `unknown`, and never guesses, when no tag is at HEAD, when several tags are, and when a tag it needs to read is stored in a pack, including a tag listed without its peeled commit in a `packed-refs` file that is not fully peeled. Clones made by a fetch often store annotated tag objects that way. A clone made with `--no-tags`, as the scheduled workflow makes, has no tags and so is always `unknown`, and that workflow declares no pins. A checkout with an `unknown` version still gets a line, labelled `unknown`, and the researcher never reads `unknown` as a mismatch.

The tag is context, not attestation. The working tree can differ from the tag, which is why a line says the checkout is at a tag rather than that it is that version.

### What the researcher sees

For each pin and each selected checkout of the upstream (other than the pinning project itself), the helper renders one fixed line from values that passed strict charsets. A value that fails is rejected, never cleaned up:

```text
pin: /home/me/src/github.com/me/app pins upstream-org/host-lib at 3.1.0 (config/pins.json); allowed checkout /home/me/src/github.com/upstream-org/host-lib-old is upstream-org/host-lib at 1.4.0. Check claims about upstream-org/host-lib at both versions; if a claim holds at one and not the other, report a `code-mismatch` with reason `unscoped` and cite the evidence from the other checkout.
```

Both roots are the ones the run lists under its projects. The skill copies a line, unchanged, into the dispatch of each family that holds a rule of the pinning project, and writes none of its own. A run keeps at most 8 lines, in a fixed order that does not depend on layer or filesystem order. Equal versions still produce a line: the helper states the versions and the researcher judges them. A line is a hint, not evidence. A candidate it leads to still has to quote evidence that validation checks, and the helper never reports a mismatch from a line.

### When no line appears

A missing line is not an error.

- **No match is silent.** A pin is dropped silently, with no note, when its project is not selected or when no selected checkout has that `origin`. The helper opens nothing for it: not the pin file, and no checkout it did not select. If a pin seems to do nothing, check the selection and the `origin` of the checkout.
- **A root outside the charset gets no line.** A project root or checkout root must be absolute, hold only `[A-Za-z0-9._/-]` and be at most 256 characters. A pair with a root that fails gets no line and a `pin-value-invalid` note. Moving the checkout fixes it.
- **Notes explain the rest.** The summary shows one `Pins:` line when there are notes, such as `Pins: pin-key-absent (0123456789ab).` A note names a project by its 12-character project key and never carries a path, a key, a value or an upstream. Notes do not degrade the run.

| Note | Meaning |
|---|---|
| `pin-file-missing` | The pin file is missing, a directory, a symlink, outside the project or unreadable. |
| `pin-file-too-large` | The pin file is over the read cap. |
| `pin-file-invalid` | The pin file is empty or is not valid JSON or JSONC. |
| `pin-key-absent` | The key does not lead to a value in the file. |
| `pin-value-invalid` | The value is not a string of the allowed form, or a root or path in the pin is outside its charset. |
| `pin-conflict` | Entries for one project, upstream and key name different files. All of them are dropped. |
| `hints-truncated` | More than 8 lines. The first 8 in order are kept. |
| `notes-truncated` | More than 8 notes. The first are kept. |

## Run it

In an interactive session:

```text
/ce:connect
```

The skill names the host it found, lists the projects it will read, what the run was narrowed to and any allow-list entries that did not match, and states the limits (see [Limits](#limits)). On a host without a recorded deny it warns that the tool limits are unverified and asks you before it dispatches. Each family is dispatched one at a time. At the end the skill prints a summary, the digest path and a candidate line for each candidate, and offers to record your decisions.

### Run a group or a few projects

```text
/ce:connect group:backend
/ce:connect projects:app,shared-lib
/ce:connect group:backend mode:headless
```

Selection words go anywhere in the arguments. Like `mode:`, they are read from the skill arguments, or from the text that started the run on a host that passes no arguments. They are never read from a file in a project. The skill passes the words to the helper unchanged, and the helper resolves them, removes identical repeats and decides conflicts, so the result is the same on every host.

The researcher is given only the selected projects, so a contradiction with a project outside the selection is not found by that run. A selection is a narrower read, not a sandbox: the researcher's read tools are still not path-scoped (see [Limits](#limits)).

### Headless mode

```text
/ce:connect mode:headless
```

Headless mode asks no question and offers nothing after the digest. It does not wait for input. It also refuses a host and version with no recorded deny, where interactive mode would ask for consent. Anything unclear becomes a stop with a reason.

Some hosts pass no arguments to a skill. On those hosts the skill reads `mode:` tokens from the text that started the run. It never reads one from a file in a project. `mode:interactive` and no token both mean interactive. Two different mode tokens, or an unknown `mode:` token, stop the run before any command.

### The four final lines

Every run ends with exactly one of these lines as its last line. The reason and the digest path come on the lines just before it. Nothing follows it.

| Final line | Meaning |
|---|---|
| `Connect complete` | The slice of rules offered to this run was fully covered, every selected project was read and nothing failed. A run that found nothing is still `complete`; its digest says "no candidate in searched scope". A `fetch:` whose candidates were all checked and none refused is `complete` too. |
| `Connect degraded` | Something was not read: a project was missing, a bound on the file inventory or on a batch was reached, a family did not finish, a file a candidate cited changed or vanished during the run (`evidence-changed`, `unresolved-source`), or an offered rule was not covered. The digest names what. A degraded run is never proof that nothing is there. A `fetch:` that refused at least one candidate is `degraded`. |
| `Connect busy` | Another run holds the lock, or its holder cannot be verified. Nothing was written and nothing was dispatched. |
| `Connect failed` | Any other stop: a bad mode token, a refused selection, a bad or unusable `fetch:`, the helper missing, a host without a recorded deny in headless mode, consent declined, no allowed projects, a malformed batch or a helper error. Nothing was published. |

A scheduler that reads the last line of the output can branch on these four.

### Headless runs on OpenCode need a host permission

A run reads and writes its work files in the state directory, and the researcher reads your allowed projects. All of that is outside the project the session runs in. OpenCode asks before it touches a path outside the project, and a run with nobody to answer is refused. On OpenCode 1.19.5, a headless run that read a work file in the state directory was refused as an `external_directory` request. The refusal ended the whole session: no final line, no digest, and the lock stayed held until the next run reclaimed it.

Before the first headless run, allow the state directory in OpenCode's own `opencode.json`. This is the host's config, not Systematic's. Use the absolute path of the state directory (see [Where the output goes](#where-the-output-goes)):

```json
{ "permission": { "external_directory": { "<state directory>/*": "allow" } } }
```

With that line, a headless run on OpenCode 1.19.5 ran the whole pipeline and ended `Connect complete`. The researcher's own definition already allows reading outside the project, so the allowed projects need no entry. Systematic never writes this line for you.

## Sweep rotation and progress

A run covers a slice of your learnings, not all of them. The helper offers at most 6 families of 8 rules each. It offers first the rules that were never covered, or whose learning changed since they were covered, and then the least recently covered ones. Inside each group it takes the projects in turn, so a slice spans projects. The order depends only on the index and on what committed runs covered, so running `ce:connect` again sweeps the whole index and then starts over with the oldest.

The researcher still searches every project the run reads for evidence. A rule that is not in this run's slice can be the other half of a contradiction with one that is.

The digest header and the summary carry one progress line:

```text
Sweep: covered 48 of 61 rules (current hashes); this run covered 48; about 1 run left in the sweep.
```

A rule counts as covered only while its learning still has the hash it had when it was covered. A run that could not read a project in full does not forget what earlier runs covered there: the coverage records of that project stay until it is read in full again, and a rule whose file could not be read stays as it was. Only a learning that is gone from a project the run read in full is forgotten. When the sweep is finished, the line says so and says the next run starts again with the least recently covered rules. Rules outside the slice are not a reason to degrade a run.

Coverage is recorded only for a run that committed. An aborted or crashed run records none.

### Each selection has its own progress

A run over a group or some projects indexes only the selected projects, and its progress line counts only those rules. Coverage is kept apart for each selection:

- **A run with no selection** keeps the coverage it always had. A group run never counts toward it, so a group run that covered a rule does not stop a later whole-list run from offering that rule.
- **A group or a pick** is identified by the set of projects it selects. The group's name is not part of the identity: two groups with the same members share one sweep, and a group that gains or loses a member starts a fresh sweep.
- **A selection of the whole list** is still a selection. It does not count as coverage for a run with no selection.
- **A narrowed run never forgets what it did not read.** The coverage of unselected projects, and of other selections, stays as it was.

The ledger holds one shared cap of 20,000 coverage records across all selections. When it is full, the oldest records that the current run did not index go first, whichever selection they belong to.

## Where the output goes

The state directory is `$XDG_STATE_HOME/systematic/connect`, or `~/.local/state/systematic/connect` when `XDG_STATE_HOME` is not set. Directories are mode 0700 and files are 0600. The helper refuses a state directory that sits inside a git checkout, is a symlink, or is inside an allowed project. Keep the path free of whitespace: when `XDG_STATE_HOME` contains whitespace, the summary prints only the candidate id, and the run record path cannot be passed to `ce:compound` as one word.

```text
<state directory>/
  lock/holder.json       the held lock (only while a run is active)
  runs/<run id>/
    digest.md            the human-readable digest
    run.json             the run record and its candidate block
  ledger.json            the minimal ledger
```

- **The digest** has three sections: candidates, connections already recorded (the target already has a learning citing the same source), and stale citations. Each candidate shows its sources with paths, fingerprints and excerpts, any counterevidence, an overlap check, and a next step. A code mismatch also shows its reason, and each piece of evidence with its project, path, line span, fingerprint and that project's checkout HEAD, or `HEAD unavailable`. A project that has no learnings is marked as read only as evidence. Free text is shown as quoted, untrusted evidence. Its header carries a `Selection:` line that names the whole allow list, the group, or the picked projects, with the selection's id.
- **The run record** (`run.json`) holds the candidate block that `ce:compound` reads when you promote a lesson. It names the selection too, and records each project's `repo` (the lowercase `owner/repo` of its `origin` remote) and the commit its HEAD names, so the record can be matched to a checkout on another machine. The helper reads both from `.git` files, runs no git command for them and opens no connection. Only GitHub remotes count, credentials in a URL are dropped, and a project with no GitHub `origin` records neither.
- **Stale citations** are a deterministic check of which `path:line` citations in your learnings still hold. A citation is `passed`, `not-in-span` (the symbol is not in the cited lines, with a flag when it is elsewhere in the file) or `unchecked` (with a reason). It reports which citations still hold. It does not promise that code has not moved. The check stops at a cap per project (500 citations). A project that reaches it is named under "Not read or not covered" in the digest and the run record keeps the counts, but the run is not marked `degraded` for that alone.
- **Retention.** Run directories older than 30 days are pruned at the start of a run. The ledger is never pruned.
- **Publishing is one rename.** A run is built in `runs/<run id>.tmp/` and renamed to `runs/<run id>/`. The ledger is updated after the rename. If a crash falls between the two, the digest exists but its candidates are not in the ledger, and the next run proposes them once more. If the ledger cannot be written after the rename, or the new ledger would pass its 16 MB limit, the old ledger stays as it was, and the run is `degraded` with the reason `ledger-write-failed`. The committed digest and run record are rewritten to say so. The next run also removes leftover `.tmp` directories.

## Promote a candidate

Only a person promotes a candidate. `ce:connect` never writes a learning. Every candidate in the summary that can be promoted comes with a line to paste. A lesson gets a line of two tokens for `ce:compound`, shown below. A contradiction or a code mismatch gets a `Review in <project>: /ce:compound-refresh path:<path>` line that names the target project's own learning, because `ce:compound` refuses both. A candidate whose next step is `investigate` has neither: the summary says to investigate it first, and there is nothing to paste yet.

```text
candidate:<run record path> candidate-id:<id>
```

Copy that line unchanged.

### A contradiction

Run `ce:compound-refresh` from the project that should change, with the exact path of the learning to review. The summary prints this line for you:

```text
/ce:compound-refresh path:docs/solutions/best-practices/export-job-retry-on-timeout-2026-02-11.md
```

Repeat `path:` for each learning. An exact path scope reviews those documents and nothing else. It shows what it will touch first and runs once per project. It refuses `mode:autofix`: a human reviews every change.

### A code mismatch

A code mismatch names one learning, in the project that should change, whose claim the code no longer supports. It has one of two reasons:

- **`stale`.** Code at the governing revision contradicts a present-tense claim. The evidence is the contradicting lines, quoted word for word.
- **`unscoped`.** The claim holds where the learning was written, but the learning does not say in which context, and positive evidence shows it false in another supported context. A fixture that merely spells a value differently is not enough.

The governing revision is the checkout of the project the claim is about. For a claim about a dependency it is the version the consuming project pins: a claim that was true at the pin is never `stale`. A learning that deliberately describes past behaviour is never a candidate.

The evidence may sit in any allowed project, the target included. To check a dependency claim, add one checkout of that dependency, at the version the consumer pins, to `connect.allow_projects`. To have the helper tell the researcher which allowed checkout is the other version, declare a pin (see [Declare dependency pins](#declare-dependency-pins)). A project with no `docs/solutions` of its own is read only as evidence and adds no rules to the sweep. The helper reads lockfiles as plain text at most and parses none, so the pin has to be shown another way: an excerpt of the consumer's `package.json` or a workflow `uses:` line, or a note from the researcher that is labelled unverified. When neither is there, the candidate's next step is `investigate`.

The helper checks provenance only: each evidence item's project, path, fingerprint, line span and word-for-word text. It cannot see a version, a pin or what the text means. The digest shows each evidence project's checkout HEAD from the run record. The HEAD is context for you, not proof that the text came from that revision, so recheck the evidence before you confirm a refresh.

A candidate with next step `refresh-learning` needs at least one evidence item and prints the same exact-path line as a contradiction, with the evidence listed beside it:

```text
/ce:compound-refresh path:docs/solutions/best-practices/export-route-rewrites-paths-2026-02-11.md
```

A candidate with next step `investigate` may have no evidence, because a search that found nothing, a missing path or a partial configuration is not evidence. It has no refresh line. Check the claim yourself first. Nothing is applied automatically.

### A transferable lesson

Run `ce:compound` from the target project, with the candidate line:

```text
/ce:compound candidate:<run record path> candidate-id:<id>
```

`ce:compound` treats the run record as data. It prints `Source project:` and `Target project:` lines first, then re-verifies every fingerprint and excerpt with its own tools and checks that the target evidence still holds. A stale fingerprint stops it and tells you to run `ce:connect` again. It then writes the learning in the target project's own words and shows the full diff. It writes after you approve the diff, and not before.

A promoted learning never copies another project's text. It cites each source as `<project>:<path>@<fingerprint>` in a `## Provenance` section in the body.

### Bring a scheduled run's candidates here

A lesson found on another machine cannot be promoted from its own record: the paths in it belong to a runner that is gone. `fetch:` brings the candidates of one attempt of a scheduled run to your machine and re-checks them against your own checkouts, so you can promote them with the usual line. The workflow is described in [Scheduled runs](#scheduled-runs).

```text
/ce:connect fetch:<run>.<attempt>
/ce:connect fetch:<owner>/<repo>:<run>.<attempt>
```

The first form is a run of Systematic's own workflow. The second is a run in another repository that called Systematic's reusable workflow ([Call it from another repository](#call-it-from-another-repository)), and it names that repository. A bare word always means Systematic, so a report names a repository only when it is not Systematic's own. The owner and repository in a named word are case-insensitive.

`<run>` is the GitHub run id and `<attempt>` is the attempt number. Each is a positive integer, digits only. A scheduled report prints this form for each candidate, with the attempt that found it, for example `fetch:43525490720.1`, or `fetch:fro-bot/agent:43525490720.1` in another repository's report. A bare `fetch:<run>` still works for Systematic and reads the newest attempt of that run. A named word always carries the attempt. A `fetch:` word stands alone: combined with `group:` or `projects:` it stops with `conflicting-selection`, and it takes no `mode:`, because a fetch dispatches no researcher, asks nothing and observes no host.

The fetch needs the GitHub CLI (`gh`), logged in with a token that can read the Actions runs and artifacts of the repository the word names (`marcusrbrown/systematic` for a bare word). The skill runs `gh` with your own credentials, as explicit commands. Every command names github.com (`--hostname github.com` for an API call, `--repo github.com/<owner>/<repo>` for the download), because the allow-list origin is a github.com origin: `GH_HOST` or a GitHub Enterprise remote does not redirect the checks. The helper never touches the network. In order:

1. **Check the repository (a named word only).** Before any `gh` command, the skill asks the helper's `allowed-origins` operation, which reads configuration and `.git` files and nothing else, for the GitHub origin of each allowed checkout. If the helper answers that it failed, or answers without the list of origins, the skill stops and prints the helper's reason, and runs no `gh` command. A repository that is not the `origin` of one allowed checkout is refused with `origin-not-allowed`, and nothing is downloaded. To fetch from a repository, add a local checkout of it to `connect.allow_projects`. A repository that two or more allowed checkouts share is refused with `repo-ambiguous`.
2. **Check the run before downloading anything.** Its event must be `schedule` or `workflow_dispatch`. A run started by a pull request is refused whatever its artifacts hold. A bare word also needs the run's workflow to be `.github/workflows/connect.yaml` or `.github/workflows/connect-scheduled.yaml`, Systematic's own wrapper. It reads no `referenced_workflows`, so Systematic's own fetch does not depend on the proof below. A run of any other workflow is refused as `not-a-connect-run`.
3. **Prove where a named run came from.** A named run's own workflow is the caller's wrapper, which proves nothing, so the skill reads the named attempt's `referenced_workflows` and never another attempt's, and hands the text `gh` printed to the helper's `verify-provenance` operation. The helper decides, not the model: it takes no lock, reads no network or configuration and writes nothing. Exactly one entry must name `marcusrbrown/systematic/.github/workflows/connect.yaml` (owner and repository without regard to case, the file path exactly) with a full 40-character commit SHA. GitHub's compare API must then show that commit as `behind` or `identical` against Systematic's `main`, so it is a commit in Systematic's own history. A copy of the workflow in a fork, a workflow of another path, or a commit that is not on `main` fails. The skill sends the helper the same text a second time with the compare status, and the helper accepts only `behind` or `identical`. A field that is absent or malformed, text that is not JSON, an API error and a commit that cannot be looked up all fail closed as `provenance-unprovable`: the proof is missing, which is not a finding that the run is hostile. To fix it, check that the caller's wrapper calls `marcusrbrown/systematic/.github/workflows/connect.yaml` at a commit on Systematic's `main`, then retry; if an API call failed, retry later.
4. **Pick the artifact** named `connect-run-<run>-<attempt>`, from the attempt the word names and no other, and download it into a fresh temporary directory that is removed afterwards. A named word or an explicit attempt looks the artifact up by its exact name. A bare `fetch:<run>`, which must find the newest attempt, lists every page of the run's artifacts.
5. **Import.** The helper reads only `run.json` from that directory (a plain file of at most 2 MiB; never a symlink), as untrusted input.

The import maps each project in the record to exactly one allowed local checkout by its `origin` remote (`owner/repo`). It then recomputes every candidate id and rule id from your local roots, never trusting a recorded one, and re-verifies each cited file's fingerprint and each excerpt against your files. It inserts the accepted candidates into your local ledger as a local run, so the usual promotion lines come out unchanged, and prints them. It never changes coverage, and it writes no learning.

A candidate is refused, and named, when its evidence does not hold on your machine. The fixed reasons include:

| Reason | Meaning |
|---|---|
| `file-changed` | A cited file differs from the file the run read. The refusal names the file. |
| `repo-not-allowed` | No allowed checkout has the recorded repository as its `origin`. For a code mismatch the refusal adds one line: allow-list a checkout of the evidence repository (at the pinned version for a dependency) and retry. |
| `repo-ambiguous` | Two allowed checkouts do. The refusal lists their keys. |
| `project-without-repo` | The run recorded no GitHub remote for a project of the candidate. |
| `file-not-tracked`, `file-symlink`, `file-vanished` | A cited file is not tracked locally, is a symlink, or is gone. |
| `path-rejected` | A cited path is absolute, climbs out of its project, or is not under `docs/solutions`, `docs/plans` or `docs/brainstorms`. |
| `candidate-id-mismatch`, `rule-id-mismatch` | The record was changed after it was written. |
| `check-failed` | A local check failed, such as an excerpt that is not in its file. |

A refused candidate is not proof the lesson is wrong. A later scheduled run proposes it again while its evidence holds.

Your checkout may be at a different commit than the one the run read. That is accepted when every check passes, and the summary shows both commits for each project. A candidate you already decided locally is skipped and named. A rerun of the same fetch writes nothing new and prints the lines of the candidates that are still open.

A named fetch that passes the checks above has shown where the run came from. It does not widen what the import accepts: every project the record names is still matched to an allowed checkout by the import's own check, and a candidate whose evidence repository is not allowed is refused as `repo-not-allowed`.

If the fetch stops before the import, the skill prints one of these reasons: `origin-not-allowed`, `repo-ambiguous`, `provenance-unprovable`, `not-a-connect-run`, `unsupported-run-event`, `run-not-found`, `gh-not-authenticated`, `artifact-list-failed`, `artifact-not-found`, `artifact-expired` or `download-failed`. The first three apply to a named word only, and `run-not-found` also covers an attempt that does not exist. If `node` or the helper file is missing, or the import prints no answer, it prints `helper-unavailable`. In every case it ends with `Connect failed`. An artifact is kept for a limited time. When it has expired, tick Rejected on the candidate in the run's report, or wait for a later run to propose it again.

Fetching a run of `connect-scheduled.yaml`, Systematic's own wrapper, needs a Systematic release that includes the change that made that wrapper call the reusable workflow. An earlier skill accepts only runs of `connect.yaml` and refuses a run of `connect-scheduled.yaml` as `not-a-connect-run`. Earlier runs of `connect.yaml` still fetch on any version. If you see that refusal for a recent run, update Systematic and fetch again.

### Settle a candidate on a report

A scheduled run's report lists every candidate that is still open and has verified details, oldest first, each with a `fetch` line for the run that found it and two boxes: **Promoted** and **Rejected**. Tick Promoted after you promoted the candidate locally, or Rejected to dismiss it.

The next run reads the ticks back with the helper's `apply-ticks` operation and records each as a decision with the reason `settled in report #<n>`, where `<n>` is the report's issue number. A settled candidate leaves the list. Only the generated lines count:

- **Only the boxes the report generated.** The operation parses one delimited section of the body, outside any code fence, and each box carries the candidate id in a marker. A `- [x]` that appears inside a candidate's quoted text records nothing.
- **Only candidates the report listed.** Each body names the list of ids it rendered. A tick for an id outside that list, or for one the ledger no longer knows, is reported as unresolved. It is never fatal.
- **One decision per candidate.** Ticking both boxes is a conflict and is skipped. A tick already recorded with the same status and reason is skipped, so reading the same body twice changes nothing.
- **Only the revision the box was made for.** Each box carries the revision of its candidate as `:r<12 hex>` in its marker: a hash of the fingerprints a decision reviews (the learning's sources, the target evidence and, for a code mismatch, the evidence files). The same content always has the same revision, so it changes when the candidate's learning, target or evidence does. A tick made against another revision, whether on an older report or one left on the same report, is reported as `stale` in the `skipped` list and records nothing: nobody has decided the revised candidate. A box with no revision is a box from a report written before revisions, and nothing can show which content it was ticked for, so it is never recorded: the tick is reported as `unversioned`, and the step that reads ticks says to tick the box on the current report. After an upgrade, tick the open candidates again on the first report that has revisions. A report lists details, a fetch line and boxes for a candidate only from one stored bundle: its text, its revision and the run and attempt that hold its evidence, all from the one proposal that produced them, and only when its revision is the one the ledger holds. A candidate with no such bundle is not listed as a row. One short section after the list, headed `No verified details`, counts them and names at most 20 of their ids, oldest first, then says how many more there are. It has no fetch line and no boxes, the manifest does not hold those ids, and the rows are fitted into the size cap beside it, so the whole body stays under the cap and a backlog of them cannot push a candidate you can settle out of the report. When the list of ids would leave no room for even the oldest row, it shrinks, down to the count alone. That covers text cached before revisions, a proposal whose ledger write failed, and a candidate with no stored text. Nothing is scheduled to refresh it: it gets details again when a run proposes it with evidence that changed, and until then it cannot be settled from the report.

Once you move the workflow's pinned Systematic version to a release with revisions, settle the open rows on the current report first. They stay settle-able while the old renderer is pinned. After the move, an open row that was never proposed again with fresh details can be settled only once its evidence changes.

The ledger a scheduled run keeps is separate from your local ledger, and nothing flows between them. Promoting locally through `fetch` does not settle the candidate on the report; tick Promoted for that. The workflow in [Scheduled runs](#scheduled-runs) calls the helper's `apply-ticks` and `render-report` operations, which read these ticks and write the report body. A local run never calls either operation.

### Record the decision

After you promote or turn down a candidate, tell the ledger. In an interactive run the skill offers to do this for you. A candidate is `candidate`, `promoted` or `rejected`, and `promoted` and `rejected` carry a reason. "Context-specific, no write needed" is `rejected` with that reason. If a learning was written but the ledger update failed, `ce:compound` prints the candidate id and destination so you can record the decision. A later run also reports learnings that carry a provenance marker with no recorded decision.

The ledger suppresses a candidate whose sources and target evidence have not changed, whatever its status. A changed source reopens it as "sources changed"; changed target evidence reopens it as "target changed".

Every candidate in the digest shows its revision as `Revision: <12 hex>` (the summary repeats it under the title): a hash of the fingerprints a decision reviews, the same for the same content. When the skill records a decision it sends the revision of the digest you decided from. If the candidate's evidence is no longer what that digest showed, the helper refuses with `stale-revision`, records nothing and says to read the current digest first. A decision sent without a revision is recorded as before. A digest from a run that could not write its ledger shows the revision of the evidence it saw: a decision from it applies only if that same evidence is later written.

A code mismatch is decided one claim at a time: a `stale` and an `unscoped` finding on one claim are separate decisions, and an edited claim is a new candidate. It reopens as "sources changed" when its learning changes, and as "evidence changed" when a recorded evidence file changes or disappears. A different set of evidence over unchanged files does not reopen it. A sibling learning that cites the learning does not mark the candidate as already recorded.

## Manage the ledger

The ledger holds identities, source paths, fingerprints, statuses, reasons and rule coverage. It holds no excerpts, and it is never evidence. The helper has three ledger operations. The skill runs them as `node "$SKILL_DIR/scripts/connect.mjs" ledger <op>`, where `SKILL_DIR` is the skill's directory.

| Operation | What it does |
|---|---|
| `ledger show` | Lists entries, including open candidates whose digest was pruned, 500 at a time. The answer has `total` and `nextOffset`; pass `{ "offset": <n> }`, or `ledger show --offset <n>` on the command line, to read on until `nextOffset` is `null`. The answer also has a `coverage` block with the number of covered rules for the whole-list sweep and for each selection, labelled `group:<name>` or `projects:<a>,<b>` while the run that last covered it is kept. |
| `ledger clear` | Removes the ledger and its coverage, for every selection. The next run proposes everything again and every sweep starts over. |
| `ledger unlock` | Removes a lock that no run holds. Use it only when you know no other run is active. |

The ledger file is at version 2. A version 1 ledger is converted by the first run that writes it: its coverage becomes the whole-list sweep, and its entries are unchanged. A ledger with any other version cannot be read and is never replaced. A helper that predates version 2 reads a version 2 ledger as unreadable and overwrites nothing, so update the skill and its helper together.

A lock held by a process that has died is reclaimed by the next run without any help. `ledger unlock` is for a run that ended without releasing its lock while its host process is still alive. The skill never runs `ledger unlock` for a busy lock, and never in headless mode. The one exception is a failed `validate` whose reply does not confirm that the lock was released: the skill then unlocks the lock its own run took before it stops.

## Scheduled runs

Systematic's repository runs one headless `ce:connect` slice a day over public repositories, and posts what it found as a GitHub issue. Two workflow files do it:

- **`.github/workflows/connect.yaml`** holds the four jobs. It is a reusable workflow that runs only when another workflow calls it (`workflow_call`), and it cannot be started on its own.
- **`.github/workflows/connect-scheduled.yaml`** is Systematic's own wrapper. It owns the triggers: every day at 05:41 UTC, and `workflow_dispatch` for a manual start. It also owns the permissions ceiling and the settings, and it passes them to `connect.yaml` as inputs and secrets. It calls that workflow from the same repository, so it pins nothing.

Any repository can call `connect.yaml` from a wrapper of its own ([Call it from another repository](#call-it-from-another-repository)). Every job checks the event and the branch of the run that called it: it runs only for `schedule` or `workflow_dispatch`, and only on the calling repository's default branch. On any other branch, or from a wrapper on another trigger such as `pull_request_target`, every job is skipped.

The run is headless, so it asks nothing and decides nothing. It proposes candidates. You settle them by ticking boxes on the report ([Settle a candidate on a report](#settle-a-candidate-on-a-report)) or by fetching them to your machine ([Bring a scheduled run's candidates here](#bring-a-scheduled-runs-candidates-here)).

### Set it up

Systematic's wrapper reads five repository variables and two repository secrets, and passes each to the workflow by name. The workflow reads no repository variables itself, so every setting it uses is an input you can see in the wrapper. The wrapper turns each variable into an input, and an unset variable arrives as an empty string. The workflow treats an empty `variant` as none and an empty `step-timeout-minutes` as 40, and it fails a run whose `projects`, `parent-model` or `researcher-model` is empty.

| Name | Kind | Reaches the workflow as | What it holds |
|---|---|---|---|
| `FRO_BOT_CONNECT_PROJECTS` | Variable | `projects` | The projects to read, as `owner/repo` entries separated by whitespace or commas. Case is folded, duplicates are dropped, and a list must hold between 1 and 16 entries. An entry's checkout name, `owner__repo`, may be at most 100 characters, because the workflow reads the repository back from that name. A longer entry stops the run. |
| `FRO_BOT_CONNECT_MODEL` | Variable | `researcher-model` | Required. The researcher's model, as `provider/model`. |
| `FRO_BOT_CONNECT_VARIANT` | Variable | `variant` | Optional. A model variant for the researcher. |
| `FRO_BOT_CONNECT_STEP_TIMEOUT` | Variable | `step-timeout-minutes` | Optional. The minutes the agent step may run, as a whole number below the run job's 50-minute timeout. The default is 40. It bounds the agent step so a hung run still posts its report. |
| `FRO_BOT_MODEL` | Variable | `parent-model` | Required. The model of the parent agent that runs the skill, as `provider/model`. It is the same variable the Fro Bot workflow uses. |
| `OPENCODE_AUTH_JSON` | Secret | `OPENCODE_AUTH_JSON` | The model provider's credential. |
| `OPENCODE_CONFIG` | Secret | `OPENCODE_CONFIG` | The OpenCode configuration the action needs next to the credential. The credential alone fails provider authentication, so both are required. |

The wrapper names both secrets one by one, because `secrets: inherit` does not cross owners and a call that works for another repository has to work here the same way. The two secrets reach only the step that runs the agent, as the action's `auth-json` and `opencode-config` inputs. The first job checks that each is non-empty by comparing it to the empty string inside an expression, so only a true or false reaches a script, and the value never enters a step environment. No other job or step references them. A well-formed but wrong credential is a provider failure at run time, not a failure of that check.

A bad setting stops the run in its first job, before anything is cloned or posted, and the workflow ends red. That covers an empty secret, a missing or malformed model (the parent's as well as the researcher's), a variant that is not a variant name, an entry that is not `owner/repo`, an empty list, a list over 16 and a step timeout that is not a whole number of minutes below 50.

**Only public repositories are read.** The first job asks the GitHub API for each repository's visibility and treats an error as not public. One repository that is not public stops the whole run. The render job checks again before it saves the cache or uploads anything, and the last job checks again right before it writes, so a repository made private during the run is caught too. Both rechecks cover every repository the cached state names, shown or not: the repositories behind all stored candidates and every retained run record, including ones that have left the list. The first job runs the same check before it uploads the restored cache, and a repository that is no longer public fails the run with nothing uploaded, cached or posted. A repository that cannot be named fails the run too. To recover, delete the connect cache with `gh cache list --key connect-v1- --limit 100 --json id --jq '.[].id' | xargs -n 1 gh cache delete`. The next run then starts with an empty ledger. Each repository is cloned without credentials, at its default branch, with its history cut to the latest commit.

The four jobs split the work by what each may touch:

1. **Prepare** has read-only access. It checks the variables and the repositories, restores the ledger cache, and records the ticks left on the newest open report.
2. **Run** has a read-only token. It is the only job that runs the agent.
3. **Render** has no permissions and no secrets. It renders the report from what the run left, rechecks visibility, saves the ledger cache and checks that the save left a cache behind.
4. **Post** is the only job that can write, and it can write only issues. It writes the report and closes the reports it replaces.

Only the run job checks out any repository. It takes the called workflow's own repository, at the commit that was called, and only `.github/actions` of it: the shared agent action that the Fro Bot workflow runs too. For Systematic's wrapper that is this repository. For a caller elsewhere it is still Systematic, never the caller, so a caller cannot put its own code in the action's place. The checkout lands in `.fro-bot-actions`, keeps no credential and leaves the connect layout alone. Repository skills are off for this run (the action's `repo-skills` input is `"false"`). No job runs a script from the repository. The jobs pass files to each other as artifacts, and an artifact carries only the connect files on an allow list: the ledger, the stores behind the report, the invocation record, and each run's `run.json` and `digest.md`. These artifacts are kept for one day.

### Pin the Systematic version

The workflow installs one exact release of `@fro.bot/systematic`. The same version feeds the action's `systematic-version` input and the helper that renders the report and reads the ticks, so the skill that wrote the state and the helper that reads it are the same release. Bump it by editing `SYSTEMATIC_VERSION` at the top of `connect.yaml`. Do it with each Systematic release that changes the format of the ledger or the run records.

The value is read from the commit that was called. A caller pins `connect.yaml` at a commit, and that commit's `SYSTEMATIC_VERSION` decides which helper its runs use. Nothing a caller sets changes it.

The `fro-bot/agent` action is pinned by commit in one place, `.github/actions/fro-bot-agent/action.yml`, which this workflow and the Fro Bot workflow both run, and its pin follows Renovate. A headless run refuses a host and version that `HOST_SUPPORT_TABLE` does not list ([Supported hosts](#supported-hosts)): the run ends `Connect failed` with the reason `unsupported-host`, and the workflow turns red.

### Read the report

Each UTC date has one report, titled `ce:connect report — YYYY-MM-DD (UTC)`. A second run on the same date edits that report in place and opens no second issue. When a new date's report is posted, each older open report gets a comment, `Superseded by #<n>.`, and is closed. The workflow finds a report by its exact title and by its author, `github-actions[bot]`, which is the login the job token posts as. An issue that only looks like a report, such as one with the same title written by another account, is ignored.

The report lists the candidates that are still open and have verified details, oldest first, as many as fit under the size cap. Each candidate has:

- the sources and the target evidence, shown as quoted text,
- for a code mismatch, its reason and each evidence item as `project:path:span:HEAD`, without the excerpt (`fetch:` supplies it),
- a `fetch:<run>.<attempt>` line for the run and attempt that found it, to bring it to your machine (a report posted in another repository names it: `fetch:<owner>/<repo>:<run>.<attempt>`), and
- two boxes, **Promoted** and **Rejected**.

Tick **one** box per candidate. Ticking both is a conflict, and neither is recorded. The next run reads the ticks from the newest open report. Ticks on a closed report are ignored, so settle a candidate before the next report supersedes the report that lists it. A box ticked on any line the report did not generate records nothing.

A box you tick while a run is going is kept. Before the last job edits or closes a report, it reads that report again and ticks the same boxes in the new body, for the candidates the new body still lists. It reads only the generated boxes inside the report's decision section and never inside a code fence. The next run then records those ticks. A tick for a candidate the new body no longer lists is dropped. A tick carries only to a box of the same candidate, status and revision: a tick on a box with no revision, the format of the Systematic version a workflow pins until you bump it, carries only onto a box with none, never onto a revision-tagged box. A tick for a candidate whose content the run changed is dropped, and the new body lists it unticked so you decide it again. A candidate with no bundle for the revision the ledger holds is not listed: it is counted in the `No verified details` section, with no boxes.

The report also says how the run ended: `Connect complete`, `Connect degraded`, `Connect busy`, `Connect failed`, or no final line. A degraded or busy run is posted and the workflow stays green. A failed run, or one that began and never reported an outcome, is posted and the workflow then turns red.

The agent step has its own timeout, `FRO_BOT_CONNECT_STEP_TIMEOUT` (40 minutes by default), shorter than the run job's. A hung run is cut off at that point and the steps after it still run: the run record is read, handed on and posted, and the report says the run ended with no final line. The job's own timeout is only a backstop. When a job is cancelled or times out, every step after the agent is skipped and nothing is posted.

A failure before the report can be rendered turns the workflow red and posts nothing. This covers an agent step that stopped before `ce:connect` began, a run record that does not belong to this run, projects that differ from the allow list the workflow wrote, a store that cannot be read, a lock that is held, and, in a repository other than Systematic, a pinned helper too old for it. The first job checks the installed helper before any agent work and fails when it has no `verify-provenance` operation. The render job fails when the helper does not name your repository in the fetch lines it generates (fetch words quoted inside a candidate's text are not read), and stops before it saves the cache or uploads anything. Both say to pin a newer callee commit whose `SYSTEMATIC_VERSION` carries named fetch words. The next run starts from the last good state and reads the same open report again.

### What the cache holds

The ledger lives in a GitHub Actions cache, because no other job or run keeps files between runs. The cache holds:

- `ledger.json`, the candidates and their decisions,
- the store of candidate text that the report is rendered from,
- the manifests of the last 14 reports, which say which ticks still count, and
- `run.json` and `digest.md` for each run.

It never holds the lock, OpenCode's own state, the configuration directory or a credential. Every run saves under a new key and restores the newest one. The save is checked: the render job looks the cache up by its key afterwards, because the save step reports success even when it saved nothing. If the cache cannot be saved, or the lookup finds nothing, the report says so and the workflow ends red, because the next run may list settled candidates again.

GitHub evicts caches that go unused for seven days or push a repository over its cache limit. After an eviction, the first run starts with an empty ledger. It restarts the sweep from the beginning, forgets earlier decisions, and may list a settled candidate again. Its report opens with a notice that no cache was restored, and a tick for a candidate the ledger no longer knows is reported as unresolved.

### Fetch a candidate

The run saves its run record as an artifact named `connect-run-<run>-<attempt>`, kept for 30 days. It holds the run record and nothing else. `fetch:<run>.<attempt>` reads that attempt's artifact and no other ([Bring a scheduled run's candidates here](#bring-a-scheduled-runs-candidates-here)). After a workflow rerun, each attempt keeps its own artifact, and a candidate carried over from an earlier attempt still names that attempt. If the named artifact is missing, `fetch` reports `artifact-not-found`, and once it has expired, `artifact-expired`. It never reads another attempt in its place. Tick **Rejected** on the report, or wait for a later run to propose the candidate again.

A bare `fetch:` reads runs of `marcusrbrown/systematic` only. A named `fetch:` reads a run of an allowed repository that called Systematic's `connect.yaml` at a commit on Systematic's default branch, and refuses everything else. A copy of the workflow, in a fork or under another path, posts its own reports and ticks, but its runs cannot be fetched.

### What the credential can reach

This is a documented exposure, and it is accepted.

The agent step can read the model provider's credential and the job's token on the runner. The parent agent has shell and network access. A prompt injection hidden in the text of a public repository could try to make it leak either one. Nothing screens the report or the artifacts for secret values, because a keyword or entropy screen gives false assurance and would not stop an agent that has its own shell and network.

The mitigations narrow what a leak is worth. None of them stops the leak:

- Only public repositories are read.
- The run job's token is scoped to the job, read-only, and expires when the job ends.
- No job has a write path to any repository. The one unattended write is the report issue.
- The credential reaches only the action step.
- Artifacts between jobs carry only the connect files on the allow list.
- The report is inert: model text is fenced and neutralised, and a quoted checkbox records nothing.

If that exposure is more than you accept, do not enable the workflow, or use a provider credential that you can scope and revoke.

## Call it from another repository

A repository of your own can run the same sweep. You add one small workflow, the wrapper, that calls Systematic's `connect.yaml`. The wrapper owns the schedule and the settings. Systematic's workflow owns the jobs. The report issue, the ledger cache and the artifacts all live in the repository that calls it, and Systematic's own report and cache are not touched.

### Copy the wrapper

Save this as a workflow file in the calling repository and fill in the pin. Systematic's own wrapper, `.github/workflows/connect-scheduled.yaml`, has the same shape.

```yaml
name: Connect

on:
  schedule:
    - cron: "17 4 * * *" # pick your own time, in UTC
  workflow_dispatch:

# No permissions at the top: each job asks for its own.
permissions: {}

jobs:
  connect:
    name: Connect
    # A called workflow can only narrow what its caller grants, so this is the
    # ceiling for all four of its jobs: read for the first two, and the report
    # issue in the last one.
    permissions:
      contents: read
      issues: write
    # Pin by full 40-character commit SHA, with the release as a comment.
    # Renovate reads the comment and keeps both current.
    uses: marcusrbrown/systematic/.github/workflows/connect.yaml@<40-character SHA> # vX.Y.Z
    with:
      # Your own repository variables, passed in by name. The called workflow
      # reads no variables itself, and an unset one arrives empty.
      projects: ${{ vars.CONNECT_PROJECTS }}
      parent-model: ${{ vars.CONNECT_PARENT_MODEL }}
      researcher-model: ${{ vars.CONNECT_RESEARCHER_MODEL }}
      variant: ${{ vars.CONNECT_VARIANT }}
      step-timeout-minutes: ${{ vars.CONNECT_STEP_TIMEOUT }}
    # Both secrets, one by one: `secrets: inherit` does not cross owners.
    secrets:
      OPENCODE_AUTH_JSON: ${{ secrets.OPENCODE_AUTH_JSON }}
      OPENCODE_CONFIG: ${{ secrets.OPENCODE_CONFIG }}
```

Set no `concurrency` in the wrapper. The called workflow holds its own group, scoped to your repository, and queues runs behind one another instead of cancelling them. The `uses:` line may write the owner and repository in any case, because GitHub and the `fetch:` check both ignore it there. The path after them is exact: `.github/workflows/connect.yaml`.

The workflow runs only for `schedule` and `workflow_dispatch` and only on your repository's default branch. Keep the wrapper on the default branch, and give it no other trigger: a run from another trigger starts no job.

### Choose the commit

The commit you pin decides everything that runs. The called workflow's own `SYSTEMATIC_VERSION` names the release that supplies the skill and the helper, so the helper of your runs is the release named at your pinned commit, and nothing you set changes it. Named `fetch:` words and the report lines that carry them need a helper that has them. A release's tag commit names the previous release, because Renovate bumps `SYSTEMATIC_VERSION` after the tag, so read the value in the commit you mean to pin before you pin it. With an older helper the report would print bare words, which mean Systematic and would not fetch your run, so the render job refuses to go on: in a repository other than Systematic it fails red when any fetch word does not name your repository, before the ledger cache is saved or any artifact is uploaded. Pin a commit whose `SYSTEMATIC_VERSION` carries named fetch words, then run again.

The agent action itself is pinned inside Systematic's repository, at the commit you call, and you do not set it.

### Before the first run

Work through this list once.

1. **The agent can read the credentials.** The agent step has shell and network access, and it can read the provider credential and the job's token. A prompt injection hidden in a public repository could try to leak either. This is the exposure described in [What the credential can reach](#what-the-credential-can-reach), and it applies in your repository. Use a provider credential you can scope and revoke.
2. **Content from your repository that still reaches the agent.** The workflow turns the agent action's repository skills off (`repo-skills` is `"false"`), and it never checks out your repository: the only checkout is the called workflow's own `.github/actions`. A read of the pinned action's source (`fro-bot/agent` v0.146.0 on OpenCode v2.3.2) shows that with the setting off, your repository's `.agents/skills`, `AGENTS.md`, `CLAUDE.md`, `opencode.json` and repository plugins are not loaded, because the action turns project configuration off for every spawn. That is read from source and not observed in a live skills-off run, and `.claude/skills` and `.opencode/` plugin directories were not traced to a line. Confirm it in the agent step's log on the first run. Whatever else sits on the runner's disk, the agent can read.
3. **The report is not screened for secret values.** The report is an issue in your repository, and it is public when the repository is. It quotes excerpts of the repositories it read, and the run record is an artifact for 30 days, readable by anyone who can read your artifacts. Nothing checks either for secret values.
4. **The Actions policy must allow the callee.** An organization or repository policy may limit which actions and reusable workflows run. Allow `marcusrbrown/systematic` workflows at the pinned commit, or the policy refuses the call. A call from one organization to a public, SHA-pinned `connect.yaml` in another owner ran without a policy error in a probe, but your policy is your own, and it was not read.
5. **Issues must be enabled.** The report is an issue, written with the job token under the `issues: write` ceiling. In a repository with Issues off, the last job cannot write it.
6. **Inputs and secrets.** All inputs are strings. A required input that is empty fails the first job red, and an unset repository variable arrives as an empty string.

   | Input | Required | Default |
   |---|---|---|
   | `projects` | Yes | None. `owner/repo` entries, 1 to 16, public repositories only, separated by whitespace or commas. |
   | `parent-model` | Yes | None. `provider/model` for the parent agent. |
   | `researcher-model` | Yes | None. `provider/model` for `connections-researcher`. |
   | `variant` | No | Empty, which means none. |
   | `step-timeout-minutes` | No | Empty, which means 40. A whole number below 50. |

   Both secrets are required: `OPENCODE_AUTH_JSON` and `OPENCODE_CONFIG`. The first job fails red when either is empty.
7. **Renovate, in the calling repository.** Renovate's `github-actions` manager bumps a SHA pin and its `# vX.Y.Z` comment on its own. The pinned workflow runs with your provider credential, so a person should review each bump. Disable automerge for it, and put the rule after any preset that sets automerge for that manager, because a later rule wins:

   ```json5
   {
     packageRules: [
       {
         description: 'Review each ce:connect workflow bump by hand: it runs with provider credentials',
         matchManagers: ['github-actions'],
         matchDepTypes: ['workflow'],
         matchPackageNames: ['marcusrbrown/systematic'],
         automerge: false,
       },
     ],
   }
   ```

   Check it with a simulated update before you rely on it: the proposal should keep a full SHA and a version comment, and it should not automerge. Systematic's own wrapper calls the workflow with `./`, so it has no pin and needs no rule.
8. **A bump can change the format.** A Systematic release that changes the format of the ledger or the run records changes what a report's boxes mean ([Settle a candidate on a report](#settle-a-candidate-on-a-report)). Before such a bump merges, settle the open rows on the current report: tick Promoted or Rejected on each. Nothing detects a format change, and Renovate does not enforce this step.
9. **Trust limits.** Read these before you allow another repository's runs.
   - **Allowing an origin trusts its workflows.** A named `fetch:` needs the repository to be the `origin` of an allowed checkout. The run record comes from a run in that repository, so it is only as trustworthy as that repository. The import still checks fingerprints, spans and excerpts against your own files, and the title and summary are still model text that nothing checks.
   - **Provenance is run-level.** The check shows that the run called Systematic's `connect.yaml` at a commit in `main`'s history. It does not tie the downloaded artifact to a job of that workflow: another job in the same run could upload an artifact with the expected name. The import's own checks are what stand between such a record and your ledger.
   - **Old callee commits stay trusted.** Any commit in `main`'s history passes the check, and there is no version floor. After a security fix in `connect.yaml`, re-pin every caller to the fixed commit. Nothing refuses a run that called an older one.

## Supported hosts

A host counts as supported only from the lowest version where a deny was observed on a real host: the researcher is dispatched, it tries shell, write, edit and web fetch, each is refused, and its read succeeds. Definition tests are regression pins and are not counted as proof. The proofs use a scripted model, so they show that the host enforces the limits. They do not show how a live model behaves.

| Host | Status | How the limits are enforced |
|---|---|---|
| OpenCode v1 | Supported | The agent's `permission:` denies `bash`, `edit`, `webfetch`, `websearch` and `task`. A blanket allow in your host config does not lift them. |
| OpenCode v2 | Supported | The same denies, plus Systematic's own tool guard (below). |
| Pi | Supported | The agent's `tools` allowlist (`Read, Grep, Glob`) reaches the delegate session as read, grep and find. |
| Claude Code | Supported | The agent's `tools` allowlist (`Read, Grep, Glob`) is what the host enforces. In a manual run with a live model, the session's tools were exactly those three. The agent also declares `disallowedTools`, but upstream reports say the host does not always enforce that for plugin subagents, so the allowlist is what counts. |

Each row is the lowest version where the limits were observed. That version and any newer release of the same host and major version are supported, so a host update does not need a new Systematic release. The versions are listed in `HOST_SUPPORT_TABLE` in `src/lib/connect-config.ts`. A release where the limits are later seen to fail goes on a known-bad list in the same file and is refused with its own reason.

The Claude Code row rests on one manual run, not on a scripted test: one live model, one version. In the run that dispatched the researcher through the `Agent` tool, the subagent reported only those three tools and called none of the others, which is its own report. The host's statement comes from the second run, a session started as the researcher, whose tool list held only Read, Grep and Glob. Read paths are not scoped, and whether a dispatched subagent can reach its parent session's MCP tools was not tested.

A version below the lowest observed one is unsupported. So is a prerelease (`2.2.8-rc.1`), a higher major version than the row names (OpenCode v1 and v2 are separate hosts, and a new major version has to be proved on its own), a host that is not in the table and a release on the known-bad list. A newer release is supported on the strength of the observation at the floor, so it has not been seen to hold on that release itself. In interactive mode an unsupported pair gets a warning that the no-write guarantee cannot be given, and the run goes on only if you agree. In headless mode it is refused with `unsupported-host`. A release on the known-bad list is the exception: its limits were seen to fail, so it is refused with `unsupported-host` in interactive mode too, and agreeing does not run it. A host whose version the skill cannot read counts as unsupported.

**Another definition of the agent keeps only its model.** If another plugin also defines `connections-researcher`, or on OpenCode v1 your own `opencode.json` or a project config does, Systematic still applies its own read-only definition: its prompt, `permission` denies and every other field replace the other entry's, and nothing from the other entry's permissions or tools is merged in. Only the other entry's `model` (and its `variant`) is kept, so you can route the researcher's model from elsewhere, and Systematic logs one warning that names the agent. A model fallback chain defined this way works for the model only; it cannot give the agent more tools. This holds on OpenCode v1 and v2. On v2 an agent definition in your own OpenCode config is applied after every plugin, so it is not replaced; the tool guard below is what keeps the researcher read-only in that case.

**On OpenCode v2, Systematic's tool guard does the enforcing.** A session-level allow rule overrides an agent's own deny on v2, and Code Mode reaches host tools that no frontmatter key can name. So Systematic registers an `execute.before` hook that refuses every call from `connections-researcher` outside a fixed list: `read`, `grep`, `glob`, `skill`, `systematic_search` and `systematic_skill`. It refuses a call made directly and a call made from inside Code Mode, and the rest of the session keeps running. The hook is registered before any agent is installed. If it cannot be registered, Systematic logs one warning and does not install `connections-researcher` at all, so the agent is never callable without its allowlist.

Pi caps a delegate at 20 turns. A family that does not finish inside the cap is marked unfinished and degrades the run. It never silently contributes nothing.

## Limits

Read these before you add a project.

- **Read tools are not path-scoped.** The researcher cannot run commands, write or fetch. Its read, grep and glob tools can still open any file your user can, not only the allowed projects. The allow list decides which projects are indexed and which paths the helper validates, and a group or a pick narrows that further. Neither is a sandbox.
- **Session MCP tools are not denied.** Tools from MCP servers connected to your session stay available to the researcher. Check what is connected before a run.
- **A digest can carry content from those reads.** A validated excerpt must come from a tracked file in an allowed project. The digest's other free text is written by the researcher after unscoped reads, and nothing screens it for secrets. Treat a digest like the learnings it quotes, keep the state directory private, and read it before you share it.
- **A pin line is a hint.** The helper states a pinned value and a checkout's tag at HEAD and nothing more. The tag is context, not attestation, a clone made with `--no-tags` always reads `unknown`, and no line is shown for a pin with no selected matching checkout.
- **Everything read is evidence.** Candidates are checked against the files, but a candidate is a proposal, and a wrong one is possible. A run that found nothing, or that is `degraded`, does not show that nothing is there.
- **The title and the summary are not checked against evidence.** The researcher writes them. The helper checks excerpts, fingerprints and paths, but not these two fields. Reads are not scoped to a path, so text from outside the allowed projects can reach the chat reply and the run records through them. Read every candidate before you promote it.
- **Coverage is self-reported.** The helper records a rule as covered from the researcher's own report of what it searched. A run steered by a hostile learning can mark rules covered without searching them. `ledger clear` resets coverage.
- **Some paths cannot be cited.** A file whose path contains a single quote, a dollar sign or a backtick is skipped, and so is a project whose root has one. The digest names the reason under "Not read or not covered".
- **A fetched record is untrusted.** It comes from a runner you do not control, and only the helper opens it. The helper re-verifies fingerprints and excerpts against your files, but the title and summary were written by a researcher on that runner and are not checked against evidence. Read every candidate before you promote it.
- **A scheduled run's agent can reach its credential.** The agent step can read the provider credential and the job's token, and nothing screens the report or the artifacts for secret values. The mitigations narrow the damage and do not prevent a leak. See [What the credential can reach](#what-the-credential-can-reach).
- **A report's ticks are only as good as the report.** A tick settles the candidate with the matching id and revision once the workflow runs a release with revisions. While it still pins an older release, a tick settles the open candidate with that id, even after the candidate reopened on different evidence. Nothing checks that you promoted it. The ledger of a scheduled run is separate from yours.
- **Promoted learnings never copy another project's text.** They are written in the target project's own words and cite their sources by project, path and fingerprint.
- **Only a human promotes.** Nothing in `ce:connect` writes a learning, edits a project, or records a decision without you.

## Privacy

The helper opens no connection at all. Apart from `fetch:` (below) and the scheduled workflow, `ce:connect` makes no network call of its own and sends nothing to anyone but your model provider. Everything a run reads and writes is on your machine. The text the researcher reads, and the digest, reach your model provider like any other tool result.

The one command that reaches GitHub is `fetch:`, and only when you type it. A bare `fetch:<run>` reads one run and downloads one artifact of `marcusrbrown/systematic`. A named `fetch:<owner>/<repo>:<run>.<attempt>` first asks the helper which repositories your allowed checkouts come from, reading configuration and `.git` files and nothing else. For a repository on that list it then makes three kinds of request with your own `gh` credentials: it reads the run and its attempt in that repository, it asks Systematic's repository to compare the commit that run called against `main`, and it downloads one artifact of the run. The requests carry the repository, the run id, the attempt, a commit hash and your `gh` token. For a repository that is not on the list it makes none. Nothing from your projects is uploaded. See [Privacy](/systematic/privacy/#connecting-your-projects).
